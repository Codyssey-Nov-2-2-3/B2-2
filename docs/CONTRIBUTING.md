# CONTRIBUTING

우리 팀(4인)이 자료구조 학습 노트를 함께 만들 때 지키는 협업 규칙입니다.

## 브랜치 전략 (GitHub Flow)

우리 팀은 GitHub Flow를 사용합니다. 브랜치는 `main`과 `feature/*` 두 종류만 운영하며, `develop` 같은 별도 브랜치는 만들지 않습니다.

### 브랜치별 역할

| 브랜치 | 역할 | 규칙 |
|---|---|---|
| `main` | 항상 깨지지 않는 배포 가능 상태를 유지하는 기준 브랜치 | 직접 commit·push 금지, Pull Request 머지로만 변경 |
| `feature/*` | 작업 단위 브랜치 (노트 한 편, 문서 한 건 등) | 최신 `main`에서 분기, 머지 후 삭제 |

### 브랜치 네이밍 규칙

형식은 `feature/{이름}-{작업요약}`입니다.

- `{이름}`: 영문 이름 또는 이니셜을 소문자로 씁니다.
- `{작업요약}`: 작업 내용을 나타내는 영문 소문자 단어를 하이픈(`-`)으로 연결합니다.
- 예시: `feature/dongtak-array-note`, `feature/dongtak-contributing-guide`

### 작업 흐름

1. GitHub에서 작업 단위로 Issue를 등록합니다.
2. 최신 `main`을 받습니다. (`git switch main` 후 `git pull`)
3. `feature/{이름}-{작업요약}` 브랜치를 만들어 작업합니다.
4. 커밋하고 push 한 뒤 Pull Request를 엽니다.
5. 리뷰를 받고 승인되면 `main`에 머지합니다.
6. 머지된 `feature/*` 브랜치는 삭제합니다.

### 안전 규칙

- `main`에는 직접 commit하거나 push하지 않습니다.
- 공유된 브랜치(`main` 등)에서는 `git push --force`와 `git rebase` 같은 히스토리 재작성을 하지 않습니다.

### GitHub Flow 선택 이유

1. 브랜치를 `main`과 `feature/*` 두 종류로만 운영해, 4인 팀 모두가 복잡한 규칙 없이 바로 협업을 시작할 수 있습니다.
2. 작업을 브랜치와 PR 단위로 격리해 한 사람의 작업이 `main`을 깨뜨리지 않고, `main`을 항상 배포 가능한 상태로 유지할 수 있습니다.
3. 팀원마다 다른 노트를 맡아 작은 단위로 PR을 올리고 서로 리뷰하는 우리 과제 방식에 가장 잘 맞습니다.

## 커밋 메시지 컨벤션

형식은 `타입: 구체적인 대상과 변경 내용`입니다.

### 허용 타입

| 타입 | 용도 | 예시 |
|---|---|---|
| `feat` | 새 예제나 기능 추가 | `feat: 스택 파이썬 구현 예제 추가` |
| `docs` | 문서와 노트 작성·수정 | `docs: 배열과 연결 리스트 개념 노트 작성` |
| `fix` | 오류와 오탈자 수정 | `fix: 연결 리스트 삭제 예제의 포인터 연결 오류 수정` |
| `refactor` | 동작은 그대로 두고 구조나 표현 개선 | `refactor: 개념 노트의 목차 순서 정리` |

### 금지 사항

다음 단어는 단독으로 쓰거나 대상이 불명확한 메시지로 쓰지 않습니다.

- `update`, `fix`, `temp`, `wip`, `final`, `bug fix`, `edit file`
- `fix:` 타입은 허용하지만, 메시지가 `fix` 한 단어뿐인 것은 금지입니다.

| 나쁜 예 | 좋은 예 |
|---|---|
| `update` | `docs: 연결 리스트 노드 구조 설명 보강` |
| `fix` | `fix: 배열 삽입 예제의 인덱스 범위 오류 수정` |
| `wip`, `temp` | 작업 단위가 끝난 뒤 내용을 드러내는 메시지로 커밋 |

### 작성 원칙

- 한 커밋에는 하나의 작업 단위만 담습니다.
- 제목만 읽어도 무엇을 바꿨는지 알 수 있어야 합니다.

## PR 규칙

모든 작업은 Issue로 시작하고, `feature/*` 브랜치에서 작업한 뒤 PR로만 `main`에 병합합니다. `main`에는 직접 commit/push하지 않습니다.

### PR 제목

- 커밋 메시지 컨벤션과 같은 형식을 씁니다: `타입: 구체적인 대상과 변경 내용`
- 예: `docs: 스택과 큐 개념 및 Python 구현 예제 노트 작성`

### PR 본문 필수 항목

PR 본문에는 아래 4가지를 반드시 포함합니다.

| 항목 | 작성 내용 |
|---|---|
| 연결 이슈 | `Closes #이슈번호` (또는 `Fixes #이슈번호`). 병합 시 이슈가 자동으로 닫힙니다. |
| 변경 사항(What) | 무엇을 추가/수정/삭제했는지 파일 단위로 적습니다. |
| 변경 이유(Why) | 왜 이 작업이 필요한지, 어떤 이슈의 어떤 항목을 해결하는지 적습니다. |
| 테스트/검증(How) | 어떻게 확인했는지 적습니다. 예: 마크다운 링크 확인, Python 3.10+ 코드 실행 결과 |

### 본문 예시

본문은 `.github/pull_request_template.md`를 기준으로 작성합니다.

```md
## 연결 이슈
- Closes #6

## 변경 사항(What)
- `src/02-stack-queue.md`에 스택과 큐 개념, Python 구현 예제 추가

## 변경 이유(Why)
- 팀원별 학습 노트 결과물 중 스택/큐 파트가 비어 있었다.

## 테스트/검증(How)
- [x] 로컬 실행/간단 테스트
- [x] 마크다운 링크 확인
- [x] Python 3.10+ 코드 실행 검증
- [x] 충돌 가능성 체크(필요 시)
```

### 작성 시 지킬 점

- PR 하나에는 이슈 하나의 작업만 담습니다. 범위가 커지면 PR을 나눕니다.
- PR을 올리기 전에 최신 `main`을 가져와 충돌 가능성을 먼저 확인합니다.
- 병합 조건: 본인을 제외한 팀원 **최소 1명의 승인(approve)**.
- 리뷰 코멘트를 받으면 수정 커밋을 추가하거나 답글로 이유를 남깁니다. 코멘트를 무시한 채 병합하지 않습니다.
- 이미 공유된 브랜치에는 `git push --force`나 `git rebase`로 히스토리를 고쳐 쓰지 않습니다.

## 코드 리뷰 규칙

### 기본 원칙

- 리뷰어는 **본인 PR을 제외한** 팀원의 PR을 리뷰합니다. 담당 리뷰어는 `.github/CODEOWNERS`를 따릅니다.
- CODEOWNERS에 지정되지 않은 파일(`docs/`, `README.md` 등)만 바꾸는 PR은 리뷰어가 자동으로 지정되지 않으므로, CODEOWNERS 파일 상단의 팀 매칭표에 따라 작성자가 리뷰어를 직접 요청합니다.
- **"LGTM", "좋아요"만 남기는 리뷰는 금지**합니다. 승인(approve)하더라도 실질적인 코멘트를 1개 이상 함께 남깁니다.
- 모든 코멘트는 **파일과 라인을 근거**로 씁니다. GitHub의 라인 코멘트 기능으로 해당 줄에 직접 답니다.

### 좋은 코멘트의 형태

코멘트는 아래 유형 중 하나 이상에 해당해야 합니다.

| 유형 | 예시 |
|---|---|
| 질문 | "`src/02-stack-queue.md` 42번 줄에서 `list.pop(0)`을 큐에 쓰면 O(n)인데, `deque`를 쓰지 않은 이유가 있나요?" |
| 대안 제안 | "15번 줄 표는 열이 5개라 모바일에서 깨질 수 있어요. 시간복잡도 열만 남기고 비고는 목록으로 빼는 건 어떨까요?" |
| 리스크 지적 | "30번 줄 링크가 `./03-tree.md`인데 실제 파일명은 `03-tree-heap.md`라 깨집니다." |
| 개선 제안 | "예제에 빈 스택에서 `pop()`할 때 동작도 한 줄 넣어 두면 이해하기 쉬울 것 같아요." |

### 나쁜 코멘트의 형태

- "LGTM" / "확인했습니다" / "👍"만 있는 코멘트
- 어느 줄을 말하는지 알 수 없는 "전체적으로 이상해요"
- 이유 없이 "이렇게 바꾸세요"라고만 하는 코멘트

### 작성자와 리뷰어의 상호작용

- 리뷰어와 작성자 사이에 **최소 1회 이상 상호작용**(답글 또는 수정 반영)이 기록으로 남아야 합니다.
- 작성자는 코멘트마다 답글을 달거나 수정 커밋을 추가하고, 반영한 커밋을 코멘트에 링크합니다.
- 반영하지 않기로 했다면 그 이유를 답글로 남깁니다.
- 리뷰어는 반영 결과를 확인한 뒤 승인합니다.

### 리뷰 톤

- 사람이 아니라 코드와 문서를 대상으로 말합니다.
- 단정 대신 질문과 제안으로 씁니다. "틀렸어요"보다 "이 경우는 어떻게 동작하나요?"로 묻습니다.
