## PR 작성 규칙

모든 작업은 Issue로 시작하고, `feature/*` 브랜치에서 작업한 뒤 PR로만 `main`에 병합한다. `main`에는 직접 commit/push하지 않는다.

### PR 제목

- 커밋 메시지 컨벤션과 같은 형식을 쓴다: `타입: 구체적인 대상과 변경 내용`
- 예: `docs: 스택과 큐 개념 및 Python 구현 예제 노트 작성`

### PR 본문 필수 항목

PR 본문에는 아래 4가지를 반드시 포함한다.

| 항목 | 작성 내용 |
|---|---|
| 연결 이슈 | `Closes #이슈번호` (또는 `Fixes #이슈번호`). 병합 시 이슈가 자동으로 닫힌다. |
| 변경 사항(What) | 무엇을 추가/수정/삭제했는지 파일 단위로 적는다. |
| 변경 이유(Why) | 왜 이 작업이 필요한지, 어떤 이슈의 어떤 항목을 해결하는지 적는다. |
| 테스트/검증(How) | 어떻게 확인했는지 적는다. 예: 마크다운 링크 확인, Python 3.10+ 코드 실행 결과 |

### 본문 예시

본문은 `.github/pull_request_template.md`를 기준으로 작성한다.

```md
## 연결 이슈
- Closes #6

## 변경 사항(What)
- `src/02-stack-queue.md`에 스택과 큐 개념, Python 구현 예제 추가

## 변경 이유(Why)
- 팀원별 학습 노트 결과물 중 스택/큐 파트가 비어 있었다.

## 테스트/검증(How)
- [x] 로컬 실행/간단 테스트
- [x] 마크다운 링크 확인
- [x] Python 3.10+ 코드 실행 검증
- [x] 충돌 가능성 체크(필요 시)
```

### 작성 시 지킬 점

- PR 하나에는 이슈 하나의 작업만 담는다. 범위가 커지면 PR을 나눈다.
- PR을 올리기 전에 최신 `main`을 가져와 충돌 가능성을 먼저 확인한다.
- 병합 조건: 본인을 제외한 팀원 **최소 1명의 승인(approve)**.
- 리뷰 코멘트를 받으면 수정 커밋을 추가하거나 답글로 이유를 남긴다. 코멘트를 무시한 채 병합하지 않는다.
- 이미 공유된 브랜치에는 `git push --force`나 `git rebase`로 히스토리를 고쳐 쓰지 않는다.

## 코드 리뷰 규칙

### 기본 원칙

- 리뷰어는 **본인 PR을 제외한** 팀원의 PR을 리뷰한다. 담당 리뷰어는 `.github/CODEOWNERS`를 따른다.
- CODEOWNERS에 지정되지 않은 파일(`docs/`, `README.md` 등)만 바꾸는 PR은 리뷰어가 자동으로 지정되지 않으므로, CODEOWNERS 파일 상단의 팀 매칭표에 따라 작성자가 리뷰어를 직접 요청한다.
- **"LGTM", "좋아요"만 남기는 리뷰는 금지**한다. 승인(approve)하더라도 실질적인 코멘트를 1개 이상 함께 남긴다.
- 모든 코멘트는 **파일과 라인을 근거**로 쓴다. GitHub의 라인 코멘트 기능으로 해당 줄에 직접 단다.

### 좋은 코멘트의 형태

코멘트는 아래 유형 중 하나 이상에 해당해야 한다.

| 유형 | 예시 |
|---|---|
| 질문 | "`src/02-stack-queue.md` 42번 줄에서 `list.pop(0)`을 큐에 쓰면 O(n)인데, `deque`를 쓰지 않은 이유가 있나요?" |
| 대안 제안 | "15번 줄 표는 열이 5개라 모바일에서 깨질 수 있어요. 시간복잡도 열만 남기고 비고는 목록으로 빼는 건 어떨까요?" |
| 리스크 지적 | "30번 줄 링크가 `./03-tree.md`인데 실제 파일명은 `03-tree-heap.md`라 깨집니다." |
| 개선 제안 | "예제에 빈 스택에서 `pop()`할 때 동작도 한 줄 넣어 두면 이해하기 쉬울 것 같아요." |

### 나쁜 코멘트의 형태

- "LGTM" / "확인했습니다" / "👍"만 있는 코멘트
- 어느 줄을 말하는지 알 수 없는 "전체적으로 이상해요"
- 이유 없이 "이렇게 바꾸세요"라고만 하는 코멘트

### 작성자와 리뷰어의 상호작용

- 리뷰어와 작성자 사이에 **최소 1회 이상 상호작용**(답글 또는 수정 반영)이 기록으로 남아야 한다.
- 작성자는 코멘트마다 답글을 달거나 수정 커밋을 추가하고, 반영한 커밋을 코멘트에 링크한다.
- 반영하지 않기로 했다면 그 이유를 답글로 남긴다.
- 리뷰어는 반영 결과를 확인한 뒤 승인한다.

### 리뷰 톤

- 사람이 아니라 코드와 문서를 대상으로 말한다.
- 단정 대신 질문과 제안으로 쓴다. "틀렸어요"보다 "이 경우는 어떻게 동작하나요?"로 묻는다.
